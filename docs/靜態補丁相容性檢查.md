## 四、必須保留為待確認的項目

1. **Session 來源檔名不同：** Session 的 `from` 是 `2026-01-07_Ragexe_1767686776_VHL_v4_clientinfo.exe`；本次上傳的是 `2026-01-07_Ragexe_1767686776_VHL_clientinfo_fixed.exe`。兩者檔名不同，需拿到 Session 所指原始 EXE 或其雜湊才能確認完全同一版本。
2. **登入模式只能擇一：** WARP 的 `LoginMode` 群組設定 `mutex: true`。舊式 `UseOldLogin` 與 `UseSSOLogin` 是不同方案，不能同時套用。此次掃描證明的是 `UseOldLogin` 2026 簽章存在，不代表已驗證登入器或伺服器封包。
3. **`NoLoginOTP` 需要實際協定確認：** WARP 腳本把 OTP 參數改成原始登入封包參數。兩份 Session 都開啟它；是否適用，須依登入器傳入資料、客戶端登入流程及伺服器封包設定決定，不可直接視為必要項目。
4. **`AlwaysAscii` 需要暫緩判定：** WARP 將它描述為不受字型或 Langtype 限制而啟用 ASCII。繁體中文字元、輸入法及字型路徑尚未測試，不能假設這項設定與中文化相容。
5. **`Translations_EN.yml` 不是繁體中文檔：** 兩份 Session 的 `$translationFile` 都顯示英文映射檔，且 `data` 欄位為空。要建立 `Translations_zhTW.yml`，必須先確認本客戶端實際字串編碼與 `Exe.SetText` 的寫入結果，避免把 UTF-8、Big5／CP950 或其他編碼錯誤寫入執行檔。
6. **`CustomDLL`／`RestoreCpsDll` 需要 DLL 實體：** WARP 預設 `Inputs/DLLSpec.yml` 提到 `cps.dll` 的匯入項目；`RestoreCpsDll` 也會在執行階段尋找 `cps.dll` 的 `uncompress`。目前未收到完整客戶端 DLL，不能確認檔案版本及匯出函式。
7. **Stove SDK：** EXE 匯入表可見 `BaseSDK.dll`、`IAPSDK.dll` 及 Stove PC SDK 函式。登入器尚未提供，所以目前不能判斷該 SDK 與登入器、SSO 或服務選擇流程的關係。
