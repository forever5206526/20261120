## 3. 為何現在不產生可直接套用的 WARP YAML

WARP 的 TranslateClient.qjs 對一般純文字替換使用 Exe.SetText(addr, replStr + "\\x00")。WARP API 文件規定，Exe.SetText(addr, text, [enc]) 的 enc 是選填；省略時按 ASCII 編碼。WARP 公開 API 的文字編碼列出 ASCII、UTF8、UTF16，未列出 Big5／CP950。WARP 的 TranslateClient 腳本可以用角括號包住十六進位資料，改走 Exe.SetHex，但前提仍是我們已經知道目標 EXE 真正使用的編碼及字型支援。

因此目前不能把這些 Unicode 中文字直接作為一般 replace 寫入 WARP Session 或 EXE。也不能僅憑檔案名稱、PE 時間戳或韓文來源字串，就猜定目標 EXE 的中文字元編碼。

## 4. WARP 翻譯規則的版本條件

WARP 的英文對照資料會依客戶端類型及 Exe.BuildDate 適用不同起訖日期。本次掃描沒有執行 WARP 的 ROC.load()，因此尚未得到 WARP 實際解析的：
- Exe.BuildDate（WARP 定義為 yyyymmdd）
- ROC.IsRenewal／ROC.IsZero／ROC.IsMain
- 對應翻譯項目的有效日期分支

PE 標頭時間不是 Exe.BuildDate 的替代值；不可將它用來判定翻譯條目是否適用。

## 5. 下一步驗證項目

1. 取得完整客戶端資料夾及 GRF／Lua／字型等資源，確認實際文字編碼與字型涵蓋範圍。
2. 取得 WARP Windows 執行環境，在原始 EXE 的副本上讀取 Exe.BuildDate、ROC 分類及 Exe.GetText 的結果。
3. 透過 WARP TestBench 建立一個單字串測試副本，先以候選編碼寫入，再確認讀回位元組、字型顯示及介面尺寸。
4. 單字串成功後才逐項增加翻譯；每個版本均保留原始 EXE、輸出 EXE、SHA-256、失敗翻譯報告及還原點。

## 6. 技術依據

- WARP TranslateClient 原始碼：Scripts/Patches/TranslateClient.qjs（專案來源：zVictorHG/WARP2026-Project）。
- WARP Exe Object：Exe.SetText(addr, text, [enc])；省略編碼時按 ASCII 處理。
- WARP Inbuilt API：公開列出的文字編碼是 ASCII、UTF8、UTF16。
- 本文件中的中文為翻譯草稿，不是已驗證的遊戲內文案，也不是可直接套用的編碼映射表。
